# Windows 网络配置工具：第四轮全面审计

日期：2026-09-09（Asia/Shanghai）  
源码基线：`14de20b42c06d1d00ce719a4e64d667525413b9f`  
范围：本次全部源码、DoH / IPv6 / DNS 预设新功能、历史修复、依赖、构建与发布材料。  
证据：[本轮复现与检查说明](./audit/2026-09-09-comprehensive/README.md)。

## 结论

**修复有效，但尚不满足稳定发布条件。** 本轮列出 13 项主要发现：9 项 P1、4 项 P2；这是整改项数量，不是可利用漏洞数量。P1 表示应在稳定发布前解决，P2 表示后续工程或兼容性整改。条件性风险已单独注明。

当前最重要的问题是：全局互斥等待超时后会绕过锁；DoH 的系统级修改没有完整事务快照；加密模板与明文回退策略读回不一致仍报告成功；恢复校验仍遗漏部分状态；恢复失败的详细提示没有呈现给用户。

前端类型检查、生产构建、Tauri 配置检查、10 个 Rust 单元测试、严格 Clippy 均通过。普通进程树超时反例已不再复现；Vite 已升至 6.4.3。不能再把上一轮原样结论套到当前版本上。

## 方法与证据边界

- 更新 codebase-memory-mcp 索引，查看架构、函数源码及事务调用链，再补充阅读 Vue、配置、脚本和文档。
- 对当前真实 Rust 事务与领域代码替换底层进程和快照 IO，进行隔离故障注入；前端使用真实 Vue 调度和实际 composable，IPC/storage 为替身。
- 执行固定 PowerShell 脚本，但所有网络/注册表命令均替换为本地 mock；未执行真实网络修改。
- 使用真实 Windows 命名互斥量验证争用，仅使用唯一的审计专用名称；使用无害计时子进程复验进程回收。
- 在线运行 Yarn 审计及 OSV Cargo.lock 查询；用 Windows normal/build 依赖树过滤部分不适用目标。OSV 首次 TLS 失败后获准重试，失败结果未用于结论。
- 检查两个现有 EXE 的签名、大小与哈希，没有运行它们。

**未实施真实 IP/DNS/路由/IPv6/DoH 写入，没有修改本机网络，没有做可恢复虚拟机中的崩溃与断网恢复验收；未做原生 WebView 端到端、release/MSI 重建、UAC 和跨登录会话实测。** 模拟状态用于验证控制流，不能证明某网络故障已经在真实机器发生。审计没有修改业务源码、依赖或锁文件。

工作区原有旧 EXE 删除保持不动。证据指纹见 `review-manifest.json`。

### N-01：锁争用超时不能退回另一命名空间

位置：`src-tauri/src/lib.rs:62–68`，调用预算在 `:117–120`。

`acquire_global_or_local` 把所有 Global 获取错误都解释为可回退，包括 `WAIT_TIMEOUT`。当实例 A 正持有 Global 锁修改网络，实例 B 等待 5 秒后改拿 Local 锁，可以同时进入事务。一次网络操作本来就可能超过 5 秒，所以同一登录会话也会触发，不只是跨会话问题。

本轮主线程持有唯一审计 Global 锁，工作线程调用真实函数，预算缩短为 150 ms，得到 `second_lock_acquired_while_global_held=true`，耗时 149 ms。没有占用应用自己的锁或执行网络操作。

修复：区分创建权限错误、等待超时和其他系统错误；争用超时必须返回 busy。机器级资源应统一使用一个可访问的锁和明确 ACL，不能让不同进程分别持有 Global/Local。`WAIT_ABANDONED` 的所有权处理已改善，但崩溃后的一致性检查仍需恢复日志配合。

### N-02：DoH 的事务范围小于实际修改范围

位置：`platform.rs:489–515、749–798、1041–1078`。

`Set/Add-DnsClientDohServerAddress` 按服务器 IP 修改系统 DoH 表，没有网卡参数。同一 DNS 用于其他网卡或 NRPT 时，也会受模板和 AutoUpgrade 改动影响。界面却把这些操作放在“目标适配器”表单中，没有表达影响范围。微软说明 AutoUpgrade 会作用于该服务器的解析，包括适配器与 NRPT 中的服务器配置。[微软 DoH API](https://learn.microsoft.com/en-us/powershell/module/dnsclient/set-dnsclientdohserveraddress?view=windowsserver2025-ps)

快照虽然查询全部 DoH 服务器，却只保留原网卡 DNS1/DNS2 的两项；回滚也只操作这两个旧地址。如果将 DNS 从 X 改为 Y，并写入 Y 的 DoH 后进程超时，回滚不会撤销 Y 的新增记录或恢复 Y 原来的模板。模拟该边界得到 `rolledBack: true`，命令记录中的恢复 DoH payload 只有旧 DNS `192.0.2.53`，没有本次修改的 `198.51.100.53`。这是“没有覆盖实际修改对象”的证据；模拟器没有操作真实系统 DoH 表。

同一地址原来为 `off` 且 fallback=false 时，恢复脚本还会强制 fallback=true，并不恢复 template；固定脚本测试记录了这个差异。

修复：按变更涉及的全部 DNS IP 保存全局条目的存在性、模板与策略；补偿时删除新增项、完整还原已存在项，并核验这些条目。界面明确系统级影响；如果要提供真正按网卡的加密策略，应使用相应的接口策略模型，而不是把系统模板表当作网卡配置。

### N-03：读回成功没有保证用户选择的加密策略

位置：`platform.rs:1352–1367`。

校验只判断期望不是 off 时，实际是否也不是 off；未比较模板、fallback、模式，期望 off 时完全跳过。

两个真实事务函数的隔离反例均返回 `success: true`：

1. 请求模板 `https://expected.example/dns-query` 且禁止明文回退，读回为另一模板并允许明文回退。
2. 请求 off，读回仍为 manual。

这会把加密策略未落实当作成功。修复：在请求规范化后比较关闭状态、实际模板和 fallback。auto 与 manual 的 UI 语义也需要规范化，因为当前读回只要模板非空就标记 manual，不能用显示标签代替系统实际策略。

### N-04：恢复仍不覆盖完整网络状态

位置：`domain.rs:273–312`；`platform.rs:868–893、919–938、1015–1028`。

恢复校验只查首个静态地址和首个网关是否存在；DNS 允许实际列表比原列表更长。本轮构造原来有第二个地址/网关、恢复后缺少它们的快照，`verify_snapshot_restored` 返回 Ok；多出一个 DNS 也返回 Ok。

恢复命令仍仅使用第一个网关，未建模路由 metric、PolicyStore、地址 SkipAsSource 等属性。原状态“非 DHCP 且无静态 IP/DNS”被恢复成 DHCP；这不是原状态，现在模式比对可能检出差异，但仍不能完成恢复。

修复：静态地址和路由按完整集合/属性比较，DNS 按完整有序列表比较；显式恢复空状态。不能支持的复杂原配置应在写入前拒绝。确认网关、DNS 空输入表示保留还是删除，并据此同时生成执行与校验规则。事务恢复还应使用持久记录，应对强制退出和重启。

### N-05：新字段查询失败不能填充为可信默认值

位置：`platform.rs:423–451、749–762`。

IPv6 查询异常被忽略并默认为 true，DoH 查询异常被忽略并返回空表；不支持功能与暂时查询失败没有区分。固定快照脚本 mock 同时抛出两类查询错误，脚本仍成功返回 `ipv6Enabled: true`、`dohSettings: {}`。这些猜测随后成为表单值和回滚依据，可能主动启用原本禁用的 IPv6 或关闭原有 DoH。

旧路由查询异常吞错已改善：同一脚本的普通路由服务失败反例现在正确抛错。剩余严格性缺口还包括数组字段缺失可被解析为空、注册表路径不存在时由 IP DHCP 推测 DNS 模式；这些情况应明确为不可用/未知，而不是完整快照。

修复：区分 unsupported、unknown 和已知值。对准备修改的字段，无法获得可靠 before 状态时应在写入前停止；只操作明确支持且读取成功的字段。

### N-06：IPv6 修改不能把真实网卡名称当通配表达式

位置：`platform.rs:425、473–476`；目标 DTO 见 `domain.rs:77–95`。

查询和 Enable/Disable-NetAdapterBinding 直接传 `-Name $adapterName`。本机 Windows 模块 CDXML 对 Set/Enable/Disable 的 Name 明确设置 `AllowGlobbing="true"`，见证据 `windows-binding-metadata.json`。固定脚本以 `Eth[1]` 为目标，mock 按真实通配语义解析，匹配到的是 `Eth1`。这属于参数语义错误，stdin JSON 不会消除通配匹配。

本轮没有重命名真实网卡，也没有执行真实 binding 修改。网页自动生成的参数表将 Supports wildcards 标为 False，与本机模块元数据不一致；因此此项依据实际模块定义，不单独依赖网页参数表。

此外，前端仍仅提交名称，没有提交用户读到的 GUID/revision；后端在写入前才按名称重新取快照，之后才比较 GUID。如果用户编辑期间网卡被替换/重命名或外部工具改过配置，缺少提交前一致性检查。读回发现身份错误以后，也仍按名称执行补偿。

修复：精确解析并绑定唯一 GUID/接口对象，通过对象操作 binding，或正确转义通配符；请求携带预期 GUID 与状态版本，写入及回滚前都核验目标。补中文、方括号名称、同名替换、编辑期间外部变更测试。

### N-07：新增 DNS / IPv6 操作强制改写 IPv4 模式

位置：`useNetworkConfig.ts:111–129、306–323`；`platform.rs:1174–1188、1202–1213`。

DHCP 网卡读回的租约 IP/DNS 被填入表单。用户仅切换 IPv6 或使用 DNS 预设再点“应用”，提交的 DTO 没有保留/DHCP/静态模式信息；后端总是执行 `set address ... static`，并将非空 DNS 设为 static。因此只改新功能也会冻结当前 DHCP 租约，影响后续租约更新和跨网络移动。

本轮捕获了真实 composable 由 DHCP 快照生成的 payload，结合后端无条件 static 分支确认；没有实际修改 DHCP。原 IPv4 静态配置工具的行为，在新增独立 DNS/IPv6 控件后需要明确重新设计。

修复：把“保持原样 / DHCP / 静态”作为显式意图，为未编辑的协议生成 no-op；或者明确限定这是“转换为静态 IPv4”的操作并呈现完整变更计划。IPv6/DoH 应能独立修改，不应要求用户把租约转为静态地址。

### N-08：最需要用户处理的恢复告警被界面隐藏

位置：`useNetworkConfig.ts:328–344`。

后端现在会在 `rolledBack=false` 时提供“恢复失败/状态未知，请手动核对”的 `rollbackMessage`，但前端只在 `rolledBack=true` 分支显示它；失败分支仅显示原始修改错误。失败响应中的最新 snapshot 也不更新 `currentSnapshot`，状态概览仍可能显示修改前的数据。

复现给出 `rollbackMessage: RECOVERY_UNKNOWN: manually restore old IP`，实际显示只有“应用失败: DNS apply failed”。后端更准确的恢复诊断尚未传到用户。

修复：无论恢复成功与否都展示恢复状态及详情；失败时更新可信现场快照或将概览标为未知，提供修改前信息供人工恢复。建议把恢复结果建模为 success/failed/unknown，而不只使用布尔值。

### N-09：缺少 DoH 能力时，off 路径也执行不存在的 cmdlet

位置：`platform.rs:489–495`；`useNetworkConfig.ts:122–127`。

foreach 在判断 off 前先调用 Get-DnsClientDohServerAddress。若系统不具备该命令，命令不存在属于终止错误，`-ErrorAction SilentlyContinue` 不能把它变成“该 DNS 无条目”。表单默认给 DNS 配置 off 对象，所以普通 IP/DNS 修改也会进入此分支；发生在 IP/DNS 已写入之后，随后还可能在恢复中再次失败。

固定脚本对“不支持命令”进行故障注入，off 请求仍失败。此项不宣称所有 Windows 版本都缺少命令。

修复：在任何写入之前做明确能力检测；unsupported 且用户未要求 DoH 改动时跳过，用户要求启用时提前报错。将最低系统要求和功能降级行为写入文档并在相应虚拟机验证。

### N-10：旧历史缺少字段应表示保留，而不是启用/关闭

位置：`useNetworkConfig.ts:378–387、404–406`。

旧版历史没有 `ipv6Enabled/doh1/doh2`，当前载入时直接补 `ipv6Enabled=true`、DoH off。即使当前网卡 IPv6 已禁用，载入旧 IPv4 历史再应用也会启用 IPv6；原历史未表达关闭 DoH 的意图，却会对历史 DNS 的全局 DoH 项执行关闭。

复现读取 IPv6=false 的系统状态，载入无扩展字段历史，表单变为 true。修复：迁移历史区分“未设置”与显式 true/false/off；缺失字段保持系统原值或生成 no-op，而不是通过默认值扩大旧预设作用范围。

### N-11：历史切换绕过了快照重绑定

位置：`useNetworkConfig.ts:153–157、391–406`。

普通缓存切换已能重新查询当前网卡快照；但 `fillFromHistory` 设置 `isApplyingHistory` 后，watcher 直接 return，函数自身也不清空/查询 `currentSnapshot`。A 上载入 B 的历史后，表单与选择是 B，快照仍为 A。

本轮分别验证普通 A→B→A 快照正确，以及跨网卡历史保留错误快照。修复：载入历史时取消旧查询，立即清空不匹配快照并仅更新目标状态；保留历史表单值，不要让后台快照覆盖它。

额外竞态观察：通过 composable API 在未完成读取时切换到缓存目标，可留下 isLoading=true；当前 UI 禁用选择会限制这一触发方式，因此未独立计为正常 UI 必现缺陷。

### N-12：Job 管理成功路径修好了，失败路径仍未封闭

位置：`platform.rs:199–220、222–229`。

Job 创建返回 None 或 AssignProcessToJobObject 返回 false 时，程序仍继续执行系统命令。创建子进程后才绑定也留下启动竞态；TerminateJobObject、kill、wait 的错误被丢弃，未确认所有成员退出就可开始回滚。微软规定绑定失败返回零，并列出嵌套 Job、权限等失败条件。[Windows Job API](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject)

这次原来的无害反例通过：预算 500 ms，558 ms 返回，后代完成标记为 false。**没有把旧版后代存活结论继续算作本轮实测失败。** 此项针对源码明确存在的条件性降级，未在本机强制造成 OS Job 绑定失败。

修复：用挂起创建/绑定后恢复或等价机制确保从首条指令起纳入 Job；创建、设置或绑定失败即停止，不执行网络命令；在剩余 deadline 内确认进程退出后再恢复网络。3 秒读回循环还应把剩余预算传给内部 10 秒查询，当前“最多 3 秒”并非实际上限。
