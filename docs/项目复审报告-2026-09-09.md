## 1. 结论

这轮修改有实质进展：原来的 PowerShell 名称直接拼接入口已消除；Tauri 配置通过 CLI 检查；网络命令移入异步阻塞任务；连续掩码及前导零校验、表单可选字段和持久化错误提示均有改进；新增的 7 个 Rust 领域测试全部通过。

但**尚不能认为“自动回滚、读回校验、网卡草稿隔离”已经可靠完成**。故障模拟确认：DNS 超时跳过回滚；读取验证失败或 DNS/网关不一致仍报告成功；回滚忽略 DNS 失败且不能完整恢复快照；切换网卡读取失败仍允许把旧 IP 提交给新网卡。

按首轮 16 项发现的原范围复核：**4 项可关闭，10 项部分解决，2 项未解决**。这不是安全评分或开发完成度百分比。新增/残留的 9 组具体整改问题见下文；建议先完成 R-01～R-04，再验证其余安全与可用性边界，暂不以“确保网络不中断”作为发布承诺。

## 3. 需要优先处理的具体问题

### R-01 — P1：执行器错误通过 `?` 返回，绕过回滚

**位置：** `src-tauri/src/platform.rs:526、538–543、562–567`，`apply_adapter_ipv4_config_transactional`。

只有 `ProcessOutput.success == false` 的部分分支触发补偿；`run_command_with_timeout` 返回 `Err`（超时、启动失败、等待错误）时，`?` 直接结束整个操作。IP 已设置后，DNS 超时尤其容易留下半完成状态。IP 步骤自身若在修改后超时，也存在状态不确定的问题。

**隔离复现：** 对实际事务函数替换执行器和快照读取，让第一条 IP 命令成功、第二条 DNS 返回超时。结果为 `Err("fixture DNS timeout")`，记录中只有这两条命令，没有任何恢复命令。[Rust 复现结果](./audit/2026-09-09-recheck/native-results.json)

**修复方向：** 首次可能产生副作用后，让所有退出路径统一进入结果处理与补偿逻辑，覆盖非零退出码、执行器异常、超时和读回失败。先确认子进程已终止，再决定重读与恢复，防止恢复和仍在执行的写命令竞争。区分“尚未修改”“部分修改”“状态未知”，不要只依赖 `?` 返回字符串。

**验收：** 每个写步骤分别注入启动失败、超时和非零退出码，都有确定的最终状态或明确恢复失败结果；不存在“第二步 Err 直接跳过补偿”的路径。

### R-02 — P1：读回校验会给出不成立的成功结论

**位置：** `platform.rs:588–604、621–623`；DNS 应用分支 `537–583`。

读取 after snapshot 失败时返回 `success: true`；读取成功时只检查 IP 与前缀，未校验网关、DNS、DHCP 模式及目标身份。于是 DNS 命令返回 0 但实际状态不符时，仍显示“已成功应用并通过读回校验”。`dns1` 为空而 `dns2` 非空时还会整个跳过 DNS 写入。

**隔离复现：**

- 写入后读取抛错，实际结果是 `success: true, rolledBack: false, snapshot: null`。
- 提交网关 `192.0.2.254`、DNS `198.51.100.53`，快照仍为网关 `192.0.2.1`、DNS `192.0.2.53`；只因 IP 匹配就通过验证。
- 仅提交 DNS2 时只记录 IP 写入，却仍返回完全成功。

**修复方向：** 按规范化变更计划逐项比较所有受影响字段。使用 `AppliedUnverified` 等显式状态或验证失败处理，不能把读取异常当完全成功。定义 DNS 的 keep/automatic/static 语义；DNS2 单独输入应明确拒绝或归一化为主 DNS。用有总时限的重试等待系统收敛，避免仅等待固定 500 ms。

**验收：** DNS/网关任一不一致都不能进入“验证通过”；读取失败展示未验证/恢复结果；验证接口 ID、模式和计划中的保留/删除语义。

### R-03 — P1：回滚既可能丢状态，也可能隐藏恢复失败

**位置：** `platform.rs:366–463`，尤其 `370–403、407–425、428–459`；快照模型 `src-tauri/src/domain.rs:28–43`。

静态回滚只恢复第一个 IPv4、第一个网关和至多两个 DNS；DNS 恢复的返回值被 `let _ = ...` 丢弃。原来没有静态地址时，函数可能不做任何恢复就返回 Ok。地址 DHCP 与 DNS 自动获取是两个独立设置，代码却在 `dhcp_enabled` 为 true 时强制把 DNS 也改成 DHCP；快照根本没有记录原 DNS 模式，因此无法还原“DHCP IP + 手工 DNS”。路由 metric、额外地址和地址属性也未完整保存。

**隔离复现：**

- 两次 DNS 恢复均返回 Err，`rollback_snapshot` 仍返回 `Ok(())`。
- 输入两地址、两网关、三个 DNS，命令记录仅涉及第一地址、第一网关及两个 DNS。
- DHCP 快照始终生成 `set dns ... source=dhcp`，不区分原 DNS 获取方式。

此外没有回滚后的再次读取，`rolledBack` 在回滚失败分支仍设为 true，容易混淆“尝试过”和“成功恢复”；IP 验证失败分支返回的 snapshot 是**回滚之前**的 after snapshot。

**修复方向：** 保存足够恢复的完整模型，或者在暂不支持多地址/复杂配置时，写入前明确拒绝并解释限制。逐条检查恢复结果，最终读回验证。拆分 `rollbackAttempted/rollbackSucceeded` 或状态枚举；失败时返回实际当前状态，不宣称恢复完毕。需要持久恢复记录才能覆盖进程崩溃。

**验收：** 多地址、多默认路由、3 个 DNS、DHCP IP + 静态 DNS、原 DNS 为空和恢复本身失败均有测试；恢复不完整时状态不能是“恢复成功”。

### R-04 — P1：网卡切换和历史载入仍能导致跨网卡误配置

**位置：** `src/composables/useNetworkConfig.ts:59–88、92–109、175–181、215–223`。

切到没有缓存的 B 网卡时只改了 `ipConfig.adapter`，未清空 A 的字段。若 B 查询失败，旧字段继续存在；提交时又使用 selectedAdapter，于是可以向 B 提交 A 的地址。

另一个问题是 `fillFromHistory` 先修改 selectedAdapter、再同步填历史字段，而 Vue watcher 后执行：它会把已填入的 B 历史值保存成 A 的草稿，随后用 B 的旧缓存覆盖刚选择的历史配置。

**实际 Vue 调度复现：** 测试使用真实 Vue `watch/nextTick`，仅替换 IPC：

- A 地址为 `192.0.2.10`，切到 B 且 B 查询失败，最终提交 `{adapter: "B", ip: "192.0.2.10"}`。
- 从 A 载入 B 的历史 `203.0.113.30`，刷新后表单却变回 B 旧草稿 `198.51.100.20`；再切回 A，A 草稿变成 `203.0.113.30`。[前端结果](./audit/2026-09-09-recheck/frontend-results.json)

仍按名称而非 GUID 绑定目标，读取和写入也没有基线 revision。已经返回 interfaceGuid 并不意味着它被用于安全绑定。`currentSnapshot` 在恢复缓存和读取失败时可能仍指向另一网卡。并发读请求缺少过期结果保护，但本次未把这一静态风险写成已经发生的 UI 故障。

**修复方向：** 将切换与历史载入改为同一明确操作：先保存旧草稿、切换身份、清理旧 snapshot，再原子设置新草稿；不要让 watcher 和载入函数共同写同一组字段。请求带序号/目标 ID，过期响应丢弃。读取失败禁止沿用其他网卡字段。后端写前重新校验稳定身份和原始状态。

**验收：** 把上述两个复现转成组件回归测试；读取失败、慢请求、历史网卡不存在/改名时均不串写。

### R-05 — P1：超时不覆盖输出线程，不能保证完整操作按时结束

**位置：** `platform.rs:98–119`；输出缓冲 `86–95`。

计时只包围父进程的 `try_wait`。父进程退出后，代码无期限 join stdout/stderr 读取线程。如果后代进程仍持有输出管道，整个函数可以继续阻塞，突破既定超时。超时分支只尝试 kill 直接子进程，忽略 kill 错误，未等待确认，也未处理后代与读取线程。stdout/stderr 使用无上限 read_to_end。

**无害实进程复现：** 只提取真实执行器，不包含任何网络读写函数；启动本地 Rust 测试进程，其父进程立即退出、后代持有管道并睡眠 2 秒。设置超时 **500 ms**，实际函数 **2066 ms** 后才返回 success。[执行器结果](./audit/2026-09-09-recheck/process-results.json)

这证明总时限失效；没有执行永久挂起测试。一个后代永久持有句柄时，当前代码缺少结束条件是源码层面的推论。最初使用 Node 定时子进程的探针未复现该行为，未用它作为缺陷证据；最终结果来自 Rust 父子进程探针。

**修复方向：** 让一个总 deadline 覆盖父进程、stdin 与输出排空；管理进程树，必要时使用 Windows Job Object；终止后确认退出并回收句柄和线程。为输出设总字节上限，保留截断标记。不要把 kill 调用等同于整个进程树已经完成。[Rust Child 生命周期](https://doc.rust-lang.org/std/process/struct.Child.html)

**验收：** 父进程退出但后代持有管道、输出超限、stdin 写失败、kill 失败均在预算内结束并报告准确状态；不能遗留与后续回滚并发的写任务。

### R-06 — P1（条件性）：可信路径仍有环境变量与 PATH 降级入口

**位置：** `platform.rs:19–39`，`get_system_binary`。

路径优先级有改善，但 SystemRoot 取自可修改的进程环境；候选路径不存在时仍返回 `PathBuf::from(binary_name)`。因此“严格路径限制”并未成立。攻击前提是启动环境或相应搜索位置受控；本次没有构建或执行恶意同名程序，也未证明完整提权链。

**只读复现：** 仅在隔离测试进程里把 SystemRoot 设为不存在的目录，函数返回相对路径 `netsh.exe`，`is_absolute == false`；随后恢复测试进程环境。见 native-results.json。

**修复方向：** 通过可信 Windows API 获取系统目录；缺少系统工具时 fail closed，不回退到 PATH。明确 x86/x64 的文件系统重定向和 PowerShell 位数；拒绝不可信二进制位置。辅助程序必须有同等路径和权限校验。

### R-07 — P1：快照仍把查询错误伪装成空配置

**位置：** `platform.rs:148–151`，固定快照脚本。

虽然设置 `$ErrorActionPreference='Stop'`，四个具体查询又使用 `-ErrorAction SilentlyContinue`，覆盖了全局设置。无法读取 IP、路由、DNS 或 DHCP 状态时，脚本仍可能输出空数组/false，并以成功结果返回；Rust 解析也使用默认值兜底。

这不只是显示问题：错误快照会被当成变更前真实状态，随后用于回滚。DHCP 查询异常可能被当成静态配置，缺失的 DNS 可能在恢复时被保留为错误的新值。

**证据等级：** 源码确认；本次没有在真实网络服务上制造故障。

**修复方向与验收：** 区分“查询成功但确实没有记录”和“查询失败”。只忽略明确识别的无记录结果，其他错误阻止写入。快照解析使用严格 DTO，必须字段缺失时失败；补上每项查询失败的测试，不允许拿不完整快照作为恢复依据。

### R-08 — P1（并发条件）：进程内 Mutex 无法保护多个应用实例

**位置：** `src-tauri/src/lib.rs:8–9、41、53`；`README.md:29`。

`tauri::async_runtime::Mutex` 加到单个 Builder 的 State，只能串行化**该进程**的写操作。两个 EXE 实例分别有各自的 Mutex，仍能交错设置 IP/DNS。README 明确宣称可避免多个应用实例冲突，与代码范围不符。也没有 revision 检查来识别用户或其他工具在快照之后的网络更改。

**证据等级：** 代码结构确认；没有实际并发修改系统网卡。

**修复方向与验收：** 采用具有合适 ACL 的命名互斥量或单一写入 helper，或者实现可靠单实例策略；锁范围覆盖快照、写入、读回和恢复。写前仍检查网卡身份及基线，避免把其他管理员的变更覆盖掉。用多个测试进程与模拟 backend 验证互斥，最终在虚拟网卡上验收。

### R-09 — P2：历史记录的可选字段和版本仍未真正校验

**位置：** `src/composables/useConfigHistory.ts:15–27、57–77`。

检查仅覆盖 adapter、ip、mask 三个字符串。`gateway: 42` 这样的记录通过检查后，在 `item.gateway?.trim()` 处抛错，使同一批原本有效的记录也被清空。`schemaVersion: 999` 的记录会直接被重新标为 1，而不是识别未知版本；id 和 timestamp 也未校验。

**复现：** 一条有效记录加一条数字网关记录，结果列表长度 0；未知版本 999 读取后变成 1。作为对照，null + 12 条有效记录确实被正确处理成 10 条，说明上一轮的部分修复已经生效。

旧 key 迁移仅在内存完成，加载后没有写回新版格式，反复加载仍会重新生成缺少的 ID/时间。删除时的存储异常仍被静默忽略，可能使用户下次打开又看到已删除项。

**修复方向与验收：** 对每个字段检查类型、长度和语义，逐条隔离坏项；显式处理旧版/当前版/未知版。迁移成功后原子保存新版并保留必要备份。混合损坏输入不能清空全部有效项，未知版本不能被悄悄重标；失败应有独立警告。
